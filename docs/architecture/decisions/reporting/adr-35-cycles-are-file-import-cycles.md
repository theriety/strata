# ADR-35: Cycle findings are file-import cycles

📌

A cycle finding reports a strongly connected component of the file-import graph that the adapters state. It names the imports whose removal breaks the cycle, or says the cut cannot be named because a file on the cycle states no imports. It never offers only symbol edges, and never an edge inside one file.

- Status: `Accepted`
- Date: `2026-11-25`
- Resolves: findings C1 and H4 of the mdc run; discovery rows disc-24, disc-29b, disc-35 and disc-36 (advice-false-moves)
- Builds on: user decisions D5 (cycle findings move to file grain) and E3 (adapters state imports; the engine never projects them)

## 🎯 Motivation

Unlace 1.0.0 ran a minimum feedback arc set (MFAS) over every multi-member strongly connected component of the hard symbol graph. It reported the component unless every member sat in one file, and suggested the MFAS break set. On mdc, every suggestion was a same-file cut, such as `applyAdapters -> recognizeAdapter` inside `parser/adapters.ts`, on a cycle that spans `parser/adapters.ts ⇄ parser/build.ts` (C1). Cutting a call inside one file cannot remove an import cycle between files, and several suggested cuts severed recursive-descent dispatch. The chooser preferred intra-file edges because they were cheapest (H4). The detail text "unlace keeps a dependency cycle in one file; to split it, break …" did not say which files or which imports were involved. The cut was also not deterministic: `applyAdapters -> recognizeAdapter` and `buildAst -> applyAdapters` tied at weight 1.0, and debug and release builds picked different edges (disc-24).

## ✅ Decision

1. **Graph.** The graph's vertices are files and its edges are the IR's `FileImport` facts (`crates/engine/src/analyze/findings/import_cycles/graph.rs`). Value and side-effect imports both count, because both load the target; module declarations do not (§6). Parallel statements between one file pair collapse into one edge that keeps every statement (specifier and line). Self-imports are left out. A component of two or more files is a cross-file cycle and becomes one `cycle` finding, located by its files in path order.
2. **Weight.** Removing the import `A → B` costs the number of distinct hard symbol edges from symbols in `A` to symbols in `B`, counted by node identity so two symbols that share a display name count twice, and at least 1, the cost of deleting the statement itself. These are the references a reader must relocate or invert before the import can go, so the cut prefers the import that carries the least code. Weights are integers, so ties are exact.
3. **Cut.** The cut is a minimum feedback arc set of the component (`import_cycles/cut.rs`). A component of up to 12 files is solved exactly by dynamic programming over file subsets: a cut is the backward-edge set of some linear order of the files, and the cheapest order is built one file at a time. Larger components take an Eades–Lin–Smyth order, then each cut edge that no longer closes a cycle is restored, and the cut is marked heuristic (`exact: false`). The order keeps every file in a bucket keyed by its outgoing-minus-incoming weight and updates only the placed file's neighbours, on adjacency lists. Each bucket is an ordered set, so a choice still falls to the lowest index, at O((V+E)·log V). The restore pass walks the kept edges once per cut edge, for O(c·(V+E)) with a cut of c imports. There is no time budget and no ILP, so the same input always yields the same cut. Among cuts of equal weight the solver prefers fewer imports; both are additive, so the exact cut is optimal on both. A remaining tie is settled by comparing the sorted `(importer, imported)` lists per file subset as the cut is built. That choice is deterministic, but it is not guaranteed to be the globally smallest list. Files are numbered by path and never by node or container id. This fixes disc-24.
4. **Finding.** `Violation.importCycle` carries `status` (`cut` or `unavailable`), `cut` (one `ImportBreak` per removed edge: `importer`, `imported`, every `statements` entry as `{line, specifier}`, the carried `references` as `{source, target}` symbol names, and `weight`), `exact`, and `filesWithoutImports`. The detail line names the file count, the first import to remove with its specifier, line and carried references, the method, and how many more imports follow. For example: "2-file import cycle; to break it, remove `./build` (line 7) from `src/parser/adapters.ts`, which carries 1 symbol reference (`parseFragment` -> `buildAst`) (exact)". The report lists each further import on its own "Also remove …" line. `breakSuggestions` is no longer set on a cycle finding, but stays readable in saved results.
5. **Unavailable, per cycle and per run.** The import graph cannot see a cycle through a file whose adapter stated no imports (`Snapshot::imports_available_for` is false). Each cross-file component of the hard symbol graph that touches such a file is therefore reported as a cycle finding with `status: unavailable` and the files that lack facts, never as an empty cut and never dropped. A symbol component whose files all state their imports is left to the import graph, which is authoritative for those files: a type-only back reference forms a symbol cycle but no import cycle, and no finding is reported. That authority stops where the adapter's facts stop. The Rust adapter does not state paths written inside macro bodies (`println!("{}", crate::a::f())`), so a cycle closed only through such a path is neither cut nor reported as unavailable. An unavailable finding reports only what no cut finding already reports. It is left out when cut findings list every file of the symbol component, or when every file states its imports. Otherwise its location is the files no cut finding lists, plus the files without facts, and `filesWithoutImports` names the files without facts. A fact-less file that a cut finding also lists is still named when the component reaches an unlisted file through it, so the cycle is never dropped. So a symbol component over `a`, `b` and a fact-less `c`, beside an import cycle `a ⇄ b`, yields the cut over `a, b` and an unavailable finding over `c` alone, never the same files twice. Its detail counts the files listed ("dependency cycle through 1 file"), not the cycle's size. Per run, `current.cycleCoverage` records `status` (`complete`, `partial` or `unavailable`) and `filesWithoutImports`. When no file states its imports (a schema 2 or 3 IR, or every adapter reported `states_imports = false`), the status is `unavailable`, so zero cycle findings never reads as zero cycles, and the report says so under the shared findings.
6. **Rust module declarations (disc-36).** A `mod child;` declaration states ownership, not a use, so it never forms or closes a cycle. Otherwise every parent `mod child;` plus the child's `use super::*` would form a 2-cycle. The adapter says which facts are declarations: the Rust adapter emits `mod child;` as `ImportKind::ModuleDeclaration`, and the graph leaves out every declaration fact. A file pair whose facts are all declarations has no edge. A pair that also states a `Value` or `SideEffect` use keeps an edge whose statements are just those uses, so a cut never names a `mod` line. The parent's uses of the child's items are separate `Value` facts, for `use child::x` and for qualified paths such as `child::run()`, `crate::a::f()` or `super::T` that resolve to another file. So a parent that calls `child::run()` while the child uses `super::Config` is a real 2-cycle and is reported. The engine no longer guesses declarations from the specifier's spelling. An earlier draft treated a bare identifier from a file with `::` specifiers as a declaration, on the premise that every `use` leaf is spelled with `::`. That premise is false: `use b;` and a qualified path with one module segment both spell a bare name, and the guess dropped real uses. A `#[cfg(test)] mod tests;` child follows the same rule: its declaration is left out, and its `use super::*` back-edge has no forward use to close a cycle. A `cfg`-disabled `mod` is still emitted as a declaration and left out like every declaration. A genuine use cycle between modules is still reported, including a parent that re-exports a child (`pub use child::x`) while the child uses the parent's items (`use super::T`). Like the TypeScript companion-folder pair `lexer/block.ts ⇄ lexer/block/mdcx.ts`, that is a real two-way dependency between files.
7. **Python (disc-35).** A parent package's `__init__.py` is not emitted as an implicit load of each submodule import, and `from pkg import sub` targets `pkg/sub.py`. This is acceptable for cycle findings. Python runs `pkg/__init__.py` first, but a cycle that closes only through an `__init__` the importer never names is a package-initialisation order issue, not an import the reader can remove. An `__init__.py` that itself imports its submodules states those imports and joins the graph normally. The src-layout blind spot recorded in disc-35 (files that look external, with `states_imports` still true) can hide a cycle without marking it unavailable. It stays open for REV02.
8. **Symbol-grain machinery.** Cycle findings no longer read the symbol MFAS. The unavailable findings above use the hard-edge components as witnesses and read only their membership, so they take it from the condensation alone and solve nothing. `solve_cycles` still solves every multi-member hard-edge SCC with the HiGHS ILP or heuristic, for one consumer: `conditional_splits`, once per profile result. Splitting an over-cap component into several files cuts symbol edges, so its `preconditions` stay `EdgeBreak`s. `hard_capacity_breaks` counts capacity findings only and never read cycle solutions. Intra-file recursion stays unreported: a symbol component inside one file container yields no import edge and no unavailable finding.

## 🔀 Alternatives considered

- **Project file edges from symbol edges.** Rejected by E3. A projected edge cannot be located by line or specifier, sees type-only references as loads, and misses side-effect imports. The adapter that owns the language states its imports.
- **Keep symbol grain and prefer file-crossing cuts.** Rejected by D5. A symbol cut that crosses files still leaves the import in place when other references use it, so it does not name the change that breaks the cycle. The 1.0.0 output also showed that cheaper same-file edges win any symbol-grain tie.
- **Reuse the core ILP for the file graph.** Rejected. Its time budget makes the exact-versus-heuristic outcome machine-dependent, and its tie-breaking follows dense ids. File components are small, so the subset DP is exact and deterministic without a solver.
- **Report an unavailable cycle per run only.** Rejected. A partially covered run (a TypeScript package beside a Rust crate whose adapter could not resolve every `use`) would hide which cycles could not be cut. A per-cycle status keeps every symbol-visible cycle in the report, and the per-run coverage covers the cycles nothing can see.
- **Drop every Rust parent/child edge.** Rejected. A parent re-exporting a child while the child uses the parent is a real two-way dependency, the same shape as the companion-folder cycle C1 asks unlace to report.

## ⚖️ Consequences

- A cross-file cycle finding names imports between two of its files, with statement lines. The eval kind `cycle_import_cut` pins this on `companion-folders` (`parser/adapters.ts ⇄ parser/build.ts`, `lexer/block.ts ⇄ lexer/block/mdcx.ts`) and fails on 1.0.0's same-file-only output. Its optional `expect` pins the import the cut must name: `adapters.ts → build.ts` line 7 and `block.ts → block/mdcx.ts` line 5.
- Result schema 12 gains `Violation.importCycle` and `CurrentTree.cycleCoverage` (DRF22 introduced the version for move term shifts). Both fields default when absent, so a saved schema-11 or early schema-12 result still reads, with coverage `complete` and the old `breakSuggestions` rendered as before.
- Goldens with cycle findings (`cyclic`, `cyclic-oversized`, `dupflat`) now name an import to remove instead of a symbol edge. No Rust golden gains a finding.
- A symbol cycle whose back edge is type-only is no longer reported. Unlace 1.0.0 reported it, because a type reference is a hard symbol edge, but a type-only import loads nothing at runtime, so the files form no import cycle. A reader upgrading from 1.0.0 sees such findings disappear. A cycle through a file without import facts is reported as unavailable, with no cut.
- `violations` ends its table with the cycle coverage note when coverage is `partial` or `unavailable`, so a CI log tells zero cycles apart from cycles the analysis could not see. Exit codes and severities do not change.
- Real Rust crates report `use` cycles between modules, often a parent facade and its children. These are true file dependencies, but in Rust they are idiomatic and not load-order hazards. Whether advice tiers should treat them differently is left to DRF21.
- Findings no longer solve the symbol MFAS: the unavailable witnesses come from the condensation, O(V+E) on the symbol graph. The MFAS still runs once per profile result, for conditional splits. The file-graph cut adds O(2^n · n²) for a component of up to 12 files, and O((V+E)·log V + c·(V+E)) above that, for V files, E imports and a cut of c. A single 3000-file component with 15000 imports cuts in under a second in a debug build.
